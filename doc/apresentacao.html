API de Reservas para Ambientes Acadêmicos com Spring Boot & Segurança de Acesso

Projeto UniReserva: gerenciamento de usuários, salas e reservas com autenticação JWT, perfis de acesso (ADMIN, STUDENT, TEACHER) e regras de autorização baseadas no usuário dono da reserva.

Fluxo principal

Ciclo de Vida de uma Reserva

Do login ao cancelamento, cada etapa está protegida com regras de negócio: verificação de conflitos, validação de existência de sala/usuário e controle de acesso por perfil e dono da reserva.

STEP 1 • Autenticação & Roles

1 Login & Perfis

O usuário realiza login e recebe um token JWT. A partir desse token o sistema identifica o perfil (ADMIN, STUDENT, TEACHER) e o usuário logado, usado nas regras de acesso às reservas.

POST /auth/login
> retorna JWT + dados do usuário (id, nome, role)
STEP 2 • Usuários & Salas

2 Gerenciamento de Usuários e Salas

Controlado por UserService e RoomService. O ADMIN pode gerenciar usuários e salas; usuários comuns têm acesso apenas às próprias informações (no caso de User).

// UserService.delete
if (!isAdmin && !isOwner) throw AccessDeniedException;
// RoomService
CRUD de salas para reserva (ADMIN)
STEP 3 • Criação com verificação de conflito

3 Criar Reserva (ReservationService.create)

Ao criar uma reserva, o sistema carrega o User e a Room, e verifica se já existe reserva conflitando no mesmo horário para a sala.

existsByRoomAndReservationDateAndStartTimeLessThanAndEndTimeGreaterThan(...);
if (conflict) throw ConflictException("Já existe uma reserva...");
STEP 4 • Permissões

4 Atualizar & Deletar com Regras de Acesso

Ao atualizar ou deletar, o ReservationService valida: isAdmin ou isOwner (usuário dono da reserva).

boolean isAdmin = loggedUser.getRole() == UserRole.ADMIN;
boolean isOwner = reservation.getUser().getId().equals(loggedUser.getId());
if (!isAdmin && !isOwner) throw new AccessDeniedException(...);

Arquitetura & Stack

Camadas da Aplicação

O projeto segue uma arquitetura em camadas: Controller → Service → Repository → Entity, com DTOs para entrada/saída e uso de Spring Security para autenticação/autorização.

Controller

Exposição dos endpoints REST. Recebe DTOs, chama services, retorna DTOs de resposta.

ReservationController, UserController, AuthController...

Service

Regras de negócio. Aqui ficam a verificação de conflitos de horário e as checagens de permissão (ADMIN ou dono).

ReservationServiceImpl, UserServiceImpl...

Repository

Interfaces JPA para acesso ao banco. Consultas como existsBy... e findByUserId.

Security & DTOs

Spring Security com JWT para autenticação e controle de endpoints. DTOs separam a API da camada de persistência.

Segurança & Regras

Quem pode fazer o quê?

Perfis de Acesso (Roles)

O sistema utiliza UserRole para diferenciar permissões. As regras principais:

  • ADMIN — gerencia todos os usuários, salas e reservas.
  • STUDENT — consegue visualizar e alterar apenas suas próprias reservas.
  • TEACHER — mesma regra de STUDENT para reservas.
if (!isAdmin && !isOwner) throw new AccessDeniedException(...);

Regras de Reserva

O ReservationServiceImpl garante que:

  • Não é possível criar reserva com horário conflitando em uma mesma sala.
  • Apenas ADMIN ou o usuário dono podem atualizar/deletar uma reserva.
  • A atualização também pode verificar conflitos quando data/hora/sala forem alterados.
// Exemplo de permissão no delete:
Reservation reservation = reservationRepository.findById(id)...
validarPermissaoSobreReserva(reservation);
reservationRepository.delete(reservation);
